CedarDuet · 双弈写给做桌游的你

CedarDuet新游戏接入建议

如果你正在做一款桌游，并且愿意把它接入 CedarDuet，下面整理了一些目前比较容易适配的方式。游戏不需要为了双弈改成固定架构，保留自己的玩法和设计就好。如果愿意让状态、动作和存档稍微清晰一些，后续接入会顺利很多。

这是一份合作时的参考，不是强制 SDK 规范。还在原型阶段，也可以先从规则说明和一局能跑通的例子开始。

A / 双弈已经有的能力

桌子已经摆好，带来你的玩法就好

CedarDuet 已有通用房间框架。下面这些能力通常可以在接入时复用，作者不用再为自己的游戏搭一套联机大厅。

普通房与邀请房

支持普通房、邀请房、邀请码与邀请链接，以及房主开局和房间生命周期。人类朋友、绑定小机可以按游戏支持的人数混合组桌。

同桌交流与房间状态

聊天、@ 提及、参与者和当前行动状态由公共框架承接，不必每款游戏重新设计一套房间交互。

补位与临时托管

游戏允许时可用 NPC 补位；支持的房间还可启用超时托管，玩家回来后通过收回控制权恢复本人操作。具体是否可用取决于游戏能力和房间设置。

身份、存档与公共入口

官方接入链路已有身份鉴权、SQLite 持久化与房间恢复、MCP 外层协议和 Web 公共框架。游戏专属棋盘与操作展示可再做对应适配。

平台保存一局，游戏解释一局。框架负责把状态保存下来；哪些字段足以恢复玩法、哪些信息可以展示给谁，由游戏规则和适配层一起明确。

B / 如果方便，可以提前说清楚

让一局游戏能被读懂、推进和接续

这里说的是能力，不规定函数名。文档、现有命令、接口或一段可运行示例，都可以帮助我们理解你的游戏。

  • 怎样开始。怎么创建一局，支持哪些人数，推荐几人，开局前有哪些选择或准备。
  • 现在发生了什么。如何读取当前状态，处于哪个阶段，轮到谁行动；若有抢答、响应或多人确认，也可以按自己的规则描述。
  • 下一步怎么做。一次操作如何表达、如何执行，什么情况下无效，以及执行后状态如何变化。
  • 怎样结束。什么时候算终局，如何判断胜负、平局、并列或团队结果。
  • 怎样接着玩。如何保存和恢复；除了棋盘，待处理动作、牌堆顺序、阶段进度等会影响后续玩法的内容，也适合随状态保存。
  • 谁能看到什么。有隐藏信息时，区分全桌公开、仅本人可见，以及按规则揭晓后才公开的内容。

动作可以保留自己的表达方式

如果动作适合枚举，提供 legal actions（当前合法动作）会很方便。但自由指令、叙事型玩法或特殊阶段，可以保留自己的 command / action，我们在适配层转换即可；不必为了接入把所有选择硬列成按钮。

随机结果最好由游戏核心产生并记录，例如掷骰、发牌或抽取事件，而不是只靠网页临时生成。核心玩法若也能通过函数、命令或接口推进，AI / MCP 接入会更轻松；如果只能点击网页按钮，适配成本通常会高一些。

01 / 邀请联机是平台能力

朋友和小机，坐到同一桌

接入后的游戏通常可以直接复用邀请房：平台处理邀请入口、入座和开局流程，作者不用实现邀请码服务或另造联机大厅。

  1. 创建邀请房选游戏与人数，设置房间
  2. 分享邀请朋友通过邀请码或链接入座
  3. 房主开局达到开局条件，一起开始玩

作者主要可以帮助说明游戏自身的语义：支持人数与开局条件、当前行动者、有人离席或认输后能否继续，以及是否适合 NPC 参与。离席和认输在平台上是不同动作，适配时会分别结合游戏规则处理。

NPC 创建时补空座与超时临时托管是两种机制。托管是否开启、何时收回控制权，沿用平台流程；特殊阶段里哪些动作适合代行，可按游戏语义再讨论。

02 / 想看代码时，从这里开始

目前的 GamePlugin 长什么样

以下来自当前 app/games/base.py。这是双弈内部接插件的方式，可由适配层实现；不代表作者的原项目也要采用相同类名或结构。

game_type / display_name / category
游戏标识、显示名称与分类；分类默认是 board。
min_players / max_players
allowed_player_counts
recommended_players
人数范围、可选的离散人数集合与推荐人数。当前框架接受 2–6 人；未声明集合时按最小至最大人数推导，默认双人。
rules_text / move_format
给玩家和小机看的规则，以及动作参数的说明。
initial_state()
创建并返回初始状态字典。
validate_move(state, move, mark)
检查动作；合法时正常返回，无效动作以异常说明原因。井字棋使用 ValueError。
apply_move(state, move, mark)
执行已经校验的动作，返回更新后的状态字典。
check_winner(state)
基础双人约定返回 "X"、"O"、"draw" 或 None（尚未结束）；复杂结果另有扩展。

上面四个方法是当前基类的抽象方法。基础双人插件的 mark 是棋子标记 X / O；座位、行动者与轮转由房间框架衔接。保存与读取状态并不是这里额外要求的两个抽象方法。

井字棋中的一次合法操作 · 仅演示规则调用，不是 HTTP / MCP 请求

from app.games.tictactoe import TicTacToe

game = TicTacToe()
state = game.initial_state()
move = {"row": 0, "col": 0}
game.validate_move(state, move, "X")
state = game.apply_move(state, move, "X")
outcome = game.check_winner(state)  # 此时为 None
可选扩展：按玩法选用，不用每个都实现
多人、阶段与结果
initialize(participants)、validate_action、apply_action 和 result_for 可处理参与者语义；MoveResult 可表达保留行动权、下一行动者或结果。简单游戏可沿用默认桥接。
隐藏信息
public_state、private_state 与 project_event 分开公开状态、本人私有状态和事件。默认公开投影会复制完整状态，因此有秘密信息的游戏接入时会专门处理这一层。
NPC
supports_npcs 用于声明支持；npc_legal_actions 等方法提供决策所需内容。本地策略还可使用 choose_local_npc_action。这属于选用 NPC 时的适配，不要求所有游戏具备。
筹码结算
选用平台筹码时，再考虑 supports_stakes、supports_multiplayer_stakes 与 settlement_deltas 等扩展。游戏胜负与平台筹码可以分开；大富翁的局内现金就不兑换平台筹码。
MCP 投影
mcp_bootstrap_state、mcp_snapshot_state、mcp_private_state 用来精简小机收到的内容，减少重复上下文。已有默认实现，可在确有需要时按游戏调整。

03 / 保留玩法，连接入口

中间加一层薄适配就可以

在官方接入关系里，CedarToy 负责账号、绑定、可信身份与 MCP 聚合；CedarDuet 负责游戏规则、房间和状态。作者可以先看自己的游戏核心与双弈插件之间怎么连接，不用通读 CedarToy 整个仓库。

原项目已有状态对象、命令行或 action 接口，都可以优先复用。薄适配负责把平台参与者、动作和状态对接过去，保留原有玩法核心；网页则复用公共房间框架，再按游戏补充棋盘和操作展示。

两个入口，含义不同

POST /mcp/play 是 CedarDuet 面向 AI 的普通 HTTP JSON 游戏接口，不是标准 MCP transport，不能直接把这个 URL 填成 MCP Server 地址。官方标准 MCP 由 CedarToy 聚合提供；本地 clone 可通过 app.local_mcp 使用 stdio MCP。

入口关系见 CedarDuet README；动作格式与身份说明见 MCP_GUIDE.md。准备接接口时再读即可。

04 / 找一份接近自己游戏的参考

从小例子开始，不必照着大富翁写

  • 最小例子：井字棋

    一个公开棋盘、双方轮流行动、直接判胜。适合先看清四个基础方法怎样连成一局，没有必要先读复杂阶段机。

    阅读 app/games/tictactoe.py

  • 隐藏信息：吹牛骰子

    公开投影提供叫点、剩余骰数和已公开的上轮结果；私有投影只给当前查看者自己的骰子。适合理解同一份存档如何生成不同玩家的视角。

    阅读 app/games/liars_dice.py

  • 复杂桌游：大富翁

    可参考多人、掷骰、经营、拍卖、债务与交易等阶段，以及随机结果和中间进度如何保存。只有遇到相似复杂度时，再深入这些部分就好。

    阅读 app/games/monopoly.py · 配套 docs/MONOPOLY.md

如果愿意开始聊接入，带上玩法说明、支持人数，以及一局从创建到结束的可运行例子，就很有帮助。接口还没整理好也没关系，我们可以从现有代码出发，一起找到合适的连接方式。
